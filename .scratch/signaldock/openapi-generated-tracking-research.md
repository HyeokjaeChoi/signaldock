# Research on Git tracking for OpenAPI generated code

Research date: 2026-10-08. Scope: OpenAPI Generator `kotlin` and `typescript-fetch`.
Status: after this research, the user adopted option 1 of revised Q91. The agreement is Git tracking plus regeneration checks for both OpenAPI and jOOQ. The findings below predate the decision. They are not results from actual generation or CI verification.

## Conclusions

The ability to regenerate code is not sufficient reason to exclude it from Git. Reproducibility, change review, and JSON semantic validation are separate concerns. The official sources below describe generation controls. They do not decide SignalDock's Git policy.

- Tracking proposal: generated output can be reviewed directly in PRs. A clean regeneration must match the stored files.
- Non-tracking proposal: fewer generated files remain in the repository. To preserve change visibility, CI must provide regenerated output and a diff against the base for review.
- This comparison and the CI conditions are the researcher's proposals. Neither was an adopted policy at the time of the research.

## Reproducibility controls

| Item | Confirmed facts and proposals |
| --- | --- |
| Generator version | The official CLI provides `version-manager set <version>`. Distinguish the installed npm wrapper version from the actual Generator JAR version. The proposal is to explicitly pin the actual Generator version for both languages. [installation documentation](https://openapi-generator.tech/docs/installation/) |
| Inputs and options | Config files, `additional-properties`, `global-property`, and type/import mappings change output. Pin the spec, referenced files, execution arguments, and config together. Check options with `config-help -g kotlin` / `config-help -g typescript-fetch` in the selected version. [Customization](https://openapi-generator.tech/docs/customization/), [Usage](https://openapi-generator.tech/docs/usage/) |
| Language-specific options | Specify Kotlin `library`, `serializationLibrary`, and `dateLibrary`. Specify TypeScript naming, `withoutRuntimeChecks`, `disallowAdditionalPropertiesIfNotPresent`, `snapshot`, and other relevant options. These values affect conversion behavior as well as output structure. [Kotlin](https://openapi-generator.tech/docs/generators/kotlin/), [typescript-fetch](https://openapi-generator.tech/docs/generators/typescript-fetch/) |
| Templates | Custom templates take priority over embedded templates. Library-specific templates also have a priority order. Manage custom template files together with their application paths. Pin embedded templates through the Generator version. Official documentation also instructs users to obtain templates from the corresponding version tag. [Templating](https://openapi-generator.tech/docs/templating/) |
| Timestamp | The shared `hideGenerationTimestamp` default in v7.15.0 is `true`. However, the reviewed default Kotlin and typescript-fetch headers do not output date variables at all. One option must not be assumed to remove every time dependency from output. The core still passes `generatedDate` and `generatedYear` to templates. Custom templates also need review. [DefaultCodegen](https://github.com/OpenAPITools/openapi-generator/blob/v7.15.0/modules/openapi-generator/src/main/java/org/openapitools/codegen/DefaultCodegen.java#L275), [DefaultGenerator](https://github.com/OpenAPITools/openapi-generator/blob/v7.15.0/modules/openapi-generator/src/main/java/org/openapitools/codegen/DefaultGenerator.java#L289), [Kotlin header](https://github.com/OpenAPITools/openapi-generator/blob/v7.15.0/modules/openapi-generator/src/main/resources/kotlin-client/licenseInfo.mustache), [TypeScript header](https://github.com/OpenAPITools/openapi-generator/blob/v7.15.0/modules/openapi-generator/src/main/resources/typescript-fetch/licenseInfo.mustache) |
| TypeScript snapshot | `snapshot=true` appends the current time in `yyyyMMddHHmm` format to the npm version. The proposal is to use `false` and a fixed package version when checking reproducibility. This is separate from `hideGenerationTimestamp`. [implementation](https://github.com/OpenAPITools/openapi-generator/blob/v7.15.0/modules/openapi-generator/src/main/java/org/openapitools/codegen/languages/AbstractTypeScriptClientCodegen.java#L502) |
| Stale outputs | `--minimal-update` writes only changed files. `--skip-overwrite` and `.openapi-generator-ignore` prevent overwrites. Do not treat them as cleanup for old files from deleted schemas. The `.openapi-generator/FILES` code also records the latest output list. The Gradle task deletes the output directory only with the separate `cleanupOutput=true` setting. For CLI use, generation into a new empty directory gives a clear boundary. The proposal is to keep manual code outside directories subject to cleanup. [Usage](https://openapi-generator.tech/docs/usage/), [Ignore](https://openapi-generator.tech/docs/customization/#ignore-file-format), [FILES implementation](https://github.com/OpenAPITools/openapi-generator/blob/v7.15.0/modules/openapi-generator/src/main/java/org/openapitools/codegen/DefaultGenerator.java#L1960), [Gradle cleanup](https://github.com/OpenAPITools/openapi-generator/blob/v7.15.0/modules/openapi-generator-gradle-plugin/src/main/kotlin/org/openapitools/generator/gradle/plugin/tasks/GenerateTask.kt#L655) |

Proposed check: generate into two empty directories with the same inputs and tool environment, then compare paths and file contents. If a formatter or post-processing is used, pin its version and settings too. Check that deleting a schema leaves no old model files. This is a reproducibility verification proposal, not a result executed during this research.

## Limits of generated model review

The source evidence below is pinned to **v7.15.0**. This does not recommend the latest version or confirm SignalDock's selected version. Web documentation reflects its current content and must be checked again against the adopted version.

- Kotlin: the default optional property template produces `T?` and a default value, or `null` when no default exists. The required template adds `?` when `isNullable` is true. Thus `T?` alone cannot distinguish optional from nullable in the schema. Annotations also vary by serializer. Constructor types alone cannot guarantee the handling of an absent JSON key versus explicit `null`. [Optional template](https://github.com/OpenAPITools/openapi-generator/blob/v7.15.0/modules/openapi-generator/src/main/resources/kotlin-client/data_class_opt_var.mustache#L24), [Required template](https://github.com/OpenAPITools/openapi-generator/blob/v7.15.0/modules/openapi-generator/src/main/resources/kotlin-client/data_class_req_var.mustache#L24)
- typescript-fetch types: optional uses `?`, and nullable uses `| null`. Type declarations alone do not establish conversion function semantics. [Interface template](https://github.com/OpenAPITools/openapi-generator/blob/v7.15.0/modules/openapi-generator/src/main/resources/typescript-fetch/modelGenericInterfaces.mustache#L19)
- typescript-fetch conversion: the reviewed optional primitive branch in `FromJSON` is `json[key] == null ? undefined : json[key]`. This path converts an absent key and explicit `null` to the same value. Dates become `Date`, and `ToJSON` creates ISO strings. Model diffs must therefore review `FromJSON`/`ToJSON` along with types. [conversion template](https://github.com/OpenAPITools/openapi-generator/blob/v7.15.0/modules/openapi-generator/src/main/resources/typescript-fetch/modelGeneric.mustache#L59)
- Runtime validation: `instanceOf…` in the same template checks only required-key presence and `undefined`. It is not a validator for every field's type, range, and nullable constraints. `FromJSON` does not call it. The documentation also states that `withoutRuntimeChecks=true` casts payloads to the expected type. Its default, `false`, does not guarantee full schema validation either. [check implementation](https://github.com/OpenAPITools/openapi-generator/blob/v7.15.0/modules/openapi-generator/src/main/resources/typescript-fetch/modelGeneric.mustache#L25), [option documentation](https://openapi-generator.tech/docs/generators/typescript-fetch/)

Proposed review: use JSON fixtures with an absent key, `null`, and a valid value for all four `required × nullable` combinations. Check encode/decode results. Verify wire field names, defaults, dates, enums, and unknown-field handling with the actual selected serializer and generated client. Git tracking can make this review easier, but cannot replace verification.

## Scope and limits

Only official OpenAPI Generator documentation and source were used. AGENTS.md and issue-tracker guidance were read first. Project generation settings, actual generated output, builds, and runtime behavior were not checked. No code generation, implementation, tests, or Git policy changes were performed. jOOQ was not researched.
