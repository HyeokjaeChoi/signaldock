60-second introduction

SignalDock is a planned Android SDK for mobile event collection. It builds on my app development experience with SDK lifecycle management, delivery recovery, and artifact distribution. A successful track call means Room has committed the event. Foreground triggers and WorkManager use one sender. The server checks eventId and content for duplicates, then sends an ACK after the database commit. If the ACK is lost, the SDK resends the same ID. It updates the queue only after validating the full ACK. Planned checks cover OpenAPI generated-source drift and an independent R8 consumer app.

01

Storage responsibility and ACK application

The first Room commit confirms local storage. The server commit confirms receipt. A final Room commit applies the ACK to the queue. Each commit has a separate role.

① Room commit confirms collection
Validate input, then store it off the main thread. Collection success does not require a server connection. Store the eventId, installationId, timestamp, sdkVersion, and contract version at collection time.
② Server commit permits per-item ACKs
An eventId unique constraint prevents concurrent duplicate inserts. On a collision, compare against committed content. Database failures and rollbacks cannot produce a receipt success ACK.
③ Validate the full ACK, then commit locally
Check indexes, IDs, counts, statuses, and consistency against the immutable request list. Remove accepted and duplicate events. For known permanent rejections, atomically save diagnostics without event content and remove the events. Reset the retry failure count after the valid ACK is committed locally.

Sender lock and database transactions

Foreground triggers and the Worker use one Mutex to serialize batch selection → HTTP → ACK validation → queue update.

New track writes run independently of this lock. Keep Room transactions closed while waiting for HTTP. Release the lock after each batch, then check cancellation and execution conditions.

A 2xx response or completed Call alone does not permit queue deletion. The full ACK must be valid and its local application must commit.

Full Jitter: U(0, B)

B doubles from 10 seconds to a 5-minute cap before jitter. A uniform random delay can allow an almost immediate retry. Use a valid Retry-After if it requires a later retry. Choose and persist the next time once per failure. Foreground triggers and the Worker share it; restarts and new triggers cannot bypass the wait. Failure count alone never discards an event.

Recovery within one OkHttp Call

Connection recovery and limited status follow-ups are allowed. An intermediate failure callback alone does not increase SDK backoff. An SDK cooldown is not guaranteed between intermediate responses.

SDK retry after the final result

The sender classifies the final result and updates persistent retry state. After the wait, it creates a new Call with the same eventIds. The server has no automatic retry loop.

Delivery is not exactly once. Deduplication prevents duplicate storage and counts while the server row exists. An old event can be stored again after row deletion or a database reset. A separate batch Idempotency-Key, response cache, and Redis are outside the first release.

03

Lifecycle and resource boundaries

Cancellation, backup behavior, and database timeouts each have limits. None alone establishes whether an event still exists.

One SDK instance with fixed configuration
Use one SDK instance and configuration in the default process. Call track after suspend initialization succeeds. Concurrent calls with the same configuration share the attempt and result. Reuse a successful instance; reject different configurations. After failure, the host must explicitly call initialization again.
Initialization wait and track cancellation
An initialization caller cancels only its own wait. Shared initialization continues in process scope. Track propagates CancellationException. An event may already be committed when its caller is cancelled. Calling track again for the same action can collect it twice with different IDs.
Exclude SDK data from backup
Store the UUIDv4 installationId in noBackupFilesDir. Exclude the queue, diagnostics, retry state, and database sidecars too. Keep the host app's other backup policies. Data survives normal restarts and updates, but clearing app data, reinstalling, or using supported restore paths can lose unsent events. Not all manufacturer transfer tools are covered.
Bound database waits and blocking work
Bound admission and connection waits. Failure to obtain an admission slot returns 503 + Retry-After. Run JDBC in an IO execution area with bounded concurrency, from connection acquisition through return. A suspend function does not make JDBC non-blocking.
lock_timeout < statement_timeout
A statement timeout is not a deadline for the full transaction. Fit waits, SQL, commit, and rollback into one request budget. A timeout does not prove that storage failed, rollback completed, or resources were released. Apply limits on the same connection and prevent settings from leaking on pool reuse. Verify actual cancellation, cleanup, and commit behavior separately.
Device diagnostics and server evidence
App diagnostics provide a read-only snapshot of the queue, recent ACKs, and next retry. The Dashboard shows stored rows, lists, details, and COUNT/GROUP BY aggregates. Server receipt does not establish SDK state. The difference occurredAt − receivedAt is not a measure of network latency alone.

04

Interview questions and tradeoffs

Explain why each choice fits this release and what still needs verification.

Why focus on an SDK?

I want to extend my app development experience into public APIs, lifecycle management, offline recovery, artifact distribution, and compatibility. The Dashboard helps verify server receipt.

Why Room and WorkManager?

Room supports durable storage and atomic queue updates. WorkManager provides a delivery retry path after process termination. It does not guarantee exact scheduling or execution after force-stop.

Why OpenAPI and JSON over Protobuf?

There is no current requirement for binary transport. OpenAPI supports contract generation and change comparison. One codec for collection and queries reduces conversion and generation work. Generated scalar types and round-trip behavior still need verification.

Why use event-level idempotency?

Retries and HTTP 413 splitting can change batch membership. Each event keeps its ID. A database unique constraint prevents concurrent duplicate inserts; content comparison distinguishes duplicate from conflict. A conflict preserves the original record.

Why jOOQ instead of an ORM?

The server needs explicit handling of unique collisions, JSONB, aggregates, cursor queries, and transaction boundaries. jOOQ generates types from the Flyway schema and keeps SQL explicit. There is no measured speed comparison with an ORM.

Why not claim exactly-once delivery?

The server may commit even if the response is lost. Retry with the same ID and server deduplication provide recovery. Deduplication does not extend beyond deletion of the server row.

What evidence is planned?

Functional checks and performance measurements are pending. Planned runs cover 1,000 offline events and process restart, ACK loss after commit, conflicts, partial rejections, ambiguous ACKs, sender contention, cancellation, capacity, backup exclusions, contract drift, migrations, and an independent R8 consumer app. Record the environment, source revision or hash, and eventId reconciliation for each run.

Planned server baseline

The server baseline has 24 conditions × 3 pool sizes (2/4/8) × 3 repeats = 216 runs. Each run has 1 minute of warmup and 5 minutes of measurement, totaling at least 21 hours 36 minutes of automated runtime before setup and recovery. This is separate from available development time.

100 events/s is the target input rate; collection ACK p95 ≤ 500 ms is the acceptance target. These are not measured results, an SLA, or a capacity guarantee. Direct HTTP load does not measure SDK performance. Keep benchmark timeouts separate from normal runtime settings.

Open checks: compatible toolchain versions, generated scalar types, exact API signatures, normal-runtime database timeouts, WorkManager contention, JDBC cancellation and commit, device behavior, and R8 execution.
