# Delivery failure E2E harness (issue 21)

The design sources fix the four cases (spec section 7 rows "Normal E2E", "ACK loss", "Partial rejection", "Content conflict"; architecture "Lost ACKs and event deduplication"; spec section 8.B Q59, Q61, Q68). They leave open how to cause the failures and where the scripts live. This ADR records the choices of issue 21. It adds no product behavior and changes no product code.

## Decisions

1. **Tool: a small Python 3 proxy, not Toxiproxy.** `scripts/e2e/fault-proxy.py` uses only the Python 3 standard library and runs on the host. It forwards `POST /v1/events:batch` to the server on `127.0.0.1:8080` and has three modes: `pass`, `drop-response` (forward, let the server commit, read its answer, then reset the connection without sending it), and `mutate` (forward with one event name changed to start with a space). Toxiproxy can cut a response after the request went through, but it cannot change a request body, and partial rejection from a real SDK needs that: the SDK validates input before storing, so it cannot produce an event the server rejects. One 130-line script covers all cases, adds no image, and stays outside `docker-compose.yml`, so `docker compose up` is unchanged. Cost: Python 3 is a host prerequisite for this script only (macOS ships it; the pinned toolchain does not include it). CI does not run it.
2. **Harness shape: the real SDK on the emulator, driven through the UI.** The independent consumer app (issue 06, R8 release, Maven ZIP only) is built with `-Psignaldock.endpoint=http://10.0.2.2:8081`, the proxy. `scripts/e2e/e2e_cases.py` taps its two buttons with `adb`, reads `track()` results and `diagnostics()` from the screen (`uiautomator dump`), and reads server state from PostgreSQL (`docker compose exec db psql`) and from the Dashboard path (`127.0.0.1:5173/v1/...` with `SignalDock-Contract-Version: 1`). The demo app is not used: it is a debug build with a Compose UI, and the consumer app proves the same `track()` and `diagnostics()` calls against the published AAR. Cases 1 to 3 use the device and the proxy. Case 4 is a server property (spec section 5), so it posts directly to `127.0.0.1:8080` with the collection key.
3. **Where things live.** `scripts/e2e-delivery.sh` is the single entry (checks the stack and the emulator, builds, installs, starts and stops the proxy, runs the cases). The helpers are in `scripts/e2e/`. The script does not start the emulator or Docker, never runs `docker compose down`, and never deletes volumes. It is not part of CI (no emulator in CI). The cases leave their events in the DB: a unique name or a fresh installation keeps repeated runs independent, and every aggregate check compares before and after.
4. **What each case proves, and what it does not.** Case 2 shows the lost ACK with two sets of facts: the server row exists and the device queue still holds the event with a `NETWORK` error, then the proxy passes, the SDK resends, and the device records `duplicate` while the row set, the Dashboard count, and the first `receivedAt` stay the same. The proxy log lists every forward. In the runs, a connection reset after the request was sent was the final result of the Call (OkHttp had no other route to retry on), so each forward was one SDK attempt; the script still counts forwards, not attempts, because OkHttp may recover a stale pooled connection inside one Call (Q122). Case 3 changes only the `name` of one event, so the invalid event is a real event the SDK stored and sent, but its content on the wire differs from the stored content. Case 4 does not exercise the SDK.
5. **One visibility change in product code.** `RetrofitBatchTransport.client` (the `OkHttpClient`) changed from a local value inside the Retrofit builder to an `internal val`, so tests can assert the Q119 to Q123 settings (30/10/10/10 second timeouts, `retryOnConnectionFailure=true`, no redirects). Behavior is unchanged.

## Not verified here

- Physical devices, other API levels, the demo app's UI, and TLS (the proxy is cleartext to `10.0.2.2`, allowed for that host by ADR-0009 item 5).
- Concurrent senders and process restart (issue 20).
