# Server marks events with a tracking plan status (issue 39, spec Q155)

The user chose (Q155) that the server checks stored events against the tracking plan and marks them. The server never rejects or drops an event for plan reasons. Every event is stored as before. Each event gets a plan status: `planned`, `unplanned_event`, or `invalid_properties`. This ADR records the implementer decisions. The user can change them.

## Decisions

1. **The plan is optional (Q153).** With no plan configured, the server does not check, and an event has no status ("not checked"). Events stored before this change have no status either. On the wire the field is absent, not `null`: the contract describes this, and a client that reads `null` as "not checked" is also correct (the generated models accept both). The SDK, the ingest request, and the ACK do not change. A plan check never changes what is stored, what the ACK says, or the HTTP status.
2. **The server reads the plan file at startup from `SIGNALDOCK_TRACKING_PLAN`.** The value is a path to a file in the format of `tracking-plan/plan.json`. Unset or blank means no plan. Compose sets it to `/etc/signaldock/tracking-plan.json` and mounts `./tracking-plan/plan.json` there read-only; `SIGNALDOCK_TRACKING_PLAN_FILE` in `.env` points the mount to another file. A blank `SIGNALDOCK_TRACKING_PLAN` in `.env` or the shell reaches the server and turns the check off (Compose `${VAR-default}` keeps a blank value). The mount uses `create_host_path: false`, so a missing plan file stops `docker compose up` with an error instead of mounting a new empty directory. Why a file and not a copy in the image: the plan is the one source in `tracking-plan/plan.json` that `generate.mjs` also reads, so the server cannot drift from the generated code, and a plan change needs a restart, not a rebuild. The file is read once; there is no hot reload.
3. **An unusable plan file stops the server at start, before the database opens.** The error names the variable, the path, and every problem found. The server checks the structure and the types: `version` is 1; `events` is a non-empty array; each event has a non-empty string `name` (no duplicate names) and an array `properties`; each property has a non-empty string `key` (no duplicate keys in one event), a `type` of `string`, `integer`, `number`, or `boolean`, and a boolean `required`. It reuses the rules of `generate.mjs` for these fields only. It does not repeat the naming style (snake_case, two words, 64 characters), the descriptions, or the Kotlin rules: `generate.mjs` and `scripts/verify-contract.sh` already check the committed plan, and a name the server does not like would only produce a status, not a failure. A mismatch between the two validators is possible for a plan that is not committed; the server then accepts a plan that the generator rejects, which is the safe direction.
4. **The status is computed at ingest and stored in a new nullable column.** `events.plan_status TEXT NULL` (migration `V2__add_plan_status.sql`), with a CHECK constraint that allows only the three values. Why stored and not computed at query time: the list, the counts, and the filter then read one column, and the status says what the plan said when the event arrived. Existing rows stay `NULL`; there is no backfill, because the plan at that time is unknown and a backfill would show a status that the server never decided. No index on the column: queries narrow by `received_at` first, and an index needs a measurement first (add it later in a migration). The check is pure Kotlin in the `ingestion` module (`TrackingPlan.check`); `EventStore` calls it for each new row. The plan file is parsed in `server/app`, which already has the JSON library; `ingestion` stays free of serialization (ADR-0005).
5. **A duplicate keeps the status of the first insert.** The insert is `ON CONFLICT DO NOTHING`, and the duplicate comparison (`sameContent`) does not include the status. A resend after a plan change returns `duplicate` and leaves the stored status as it was.
6. **Check rules.** The name must match a plan event exactly (no trimming, like Q64): otherwise `unplanned_event`, whatever the properties are. For a planned name: all `required` keys present, no key outside the plan, and each value of the plan type; otherwise `invalid_properties`. A wrong type of an optional key is also `invalid_properties`. Types: `string` is a JSON string, `boolean` a JSON boolean, `number` any JSON number, `integer` a JSON number with no fraction (`5`, `5.0`, and `1e3` count; `5.5` does not; the SDK sends a `Long` as `5`, but a number with a zero fraction is a whole number in JSON).
7. **Contract change (additive, contract version stays 1).** Q65 allows compatible optional additions in the same version. `openapi/contract-v1.yaml` adds: the schema `PlanStatus` (enum `planned`, `unplanned_event`, `invalid_properties`); an optional `planStatus` on `EventReceiptSummary` and `EventReceiptDetail`; an optional `planStatus` query filter on `GET /v1/events`, `/v1/event-counts/by-name`, and `/v1/event-counts/by-time`; and a new route `GET /v1/event-counts/by-plan-status` that returns `planned`, `unplannedEvent`, `invalidProperties`, and `notChecked` (counts of the period; it takes the other exact filters and rejects `planStatus`, because it already splits by it). Why a new route and not three filtered calls: the Dashboard needs the violation count of the whole period, and one `COUNT ... FILTER` statement is one request and one snapshot. A filter on a status never matches an event that was not checked. A new status value later is a contract change, because the generated Kotlin models fail on an unknown enum value (the round-trip test shows this). `oasdiff breaking` reports no breaking change; `fixtures/contract/contract-v1.baseline.yaml` is updated in the same PR (ADR-0002 amendment), and `generated/` is regenerated with `scripts/codegen.sh`. The commands and outputs are in the issue 39 file.
8. **Dashboard.** A badge with a dot and a word (`ok` for planned, `warn` for unplanned event, `bad` for invalid properties, `idle` "Not checked" for no status) in the event list and the details; a select "Plan status" in the toolbar (and in the "More filters" disclosure at 720 px or less), applied with the other filters; a KPI card "Plan violations" with the count of `unplanned_event` plus `invalid_properties` in the shown period, and a sub line with both parts. The card shows "Not checked" when no event of the period has a status (for example when the server has no plan). The counts come from a fourth polled query (`by-plan-status`) with the filters in force except the status filter. The texts are in the English and Korean dictionaries (ADR-0015); the colors are existing tokens (ADR-0016). No new dependency.
9. **Benchmarks stay on the old path.** `perf/compose.perf.yml` sets `SIGNALDOCK_TRACKING_PLAN` to an empty value, so the load measurements (ADR-0013) still measure ingest without the check. Measuring the cost of the check is not part of this issue.

## Test mechanism

- `TrackingPlanTest` (`server/ingestion`): each status, a missing required key, an unknown key, a wrong type (also of an optional key), integer spellings.
- `TrackingPlanFileTest` (`server/app`): the committed `tracking-plan/plan.json` loads and marks its own events; unset and blank variable mean no plan; a missing file, text that is not JSON, and each structure and type error fail with a clear message.
- `PlanStatusTest` (`server/app`, real PostgreSQL): five events through the HTTP routes are all `accepted` with an unchanged ACK shape and are marked; list, details, the three filters, and the counts show the statuses; without a plan the field is absent and the events count as not checked; a duplicate keeps its first status (null and non-null); the parameter checks.
- `SchemaUpgradeTest` (`server/persistence`): `previous-data/V2.sql` holds a row written at V2; rows written at V1 are null after the upgrade (ADR-0012).
- `contract-check` and `npm run contract-check`: new round-trip fixtures with every status; the older fixtures without `planStatus` still decode.
- Dashboard tests: badge, filter, KPI, request parameters (`api.test.ts`), and the English and Korean keys (`tsc` checks that both dictionaries have the same keys).

## Not done

- No rejection or drop mode, and no setting for one (Q155).
- No hot reload of the plan, and no backfill of old rows.
- No check of value ranges, string formats, or key naming style on the server.
- No index on `plan_status`, and no measurement of the check cost.
- No change in the SDK, the ACK, `sdk/sdk-android`, or its API dump; the demo and consumer apps are unchanged.
