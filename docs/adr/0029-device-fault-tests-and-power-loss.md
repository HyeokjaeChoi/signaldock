# Device fault tests and power-loss semantics (issue 47)

ADR-0011 and ADR-0017 list four limits of the device test harness: offline is a refused connection and not airplane mode, a full disk is only injected, a WorkManager failure is only simulated, and power loss is not tested. This ADR closes the first three on an emulator and fixes the semantics of the fourth. It adds no product behavior and changes no product code. It updates the "Limits" section of ADR-0011 and the "Test limits" section of ADR-0017.

## Decisions

1. **Airplane mode is a real switch.** `FaultPhases.airplane_mode` runs `cmd connectivity airplane-mode enable` and `disable` through `UiAutomation.executeShellCommand` and waits until `ConnectivityManager.activeNetwork` is `null` or not `null`. While the network is off, `track()` succeeds, delivery ends with `lastDeliveryError.kind == NETWORK`, and all events stay in the queue. After the switch is off, the queue is delivered. The server runs on the host (`scripts/ack-server.py`, reached at `10.0.2.2`). Loopback and the device's own address do not follow airplane mode: a first try with a server on the device address gave `TIMEOUT` in one run and delivered normally in another. A route to a remote address is removed, which gives `NETWORK` at once. The test restores airplane mode in `finally`, and the script restores it in an `EXIT` trap.
2. **A full disk is real.** `FaultPhases.full_disk` reserves free space with `posix_fallocate` in a filler file until about 256 KiB are free, then calls `track()` until it returns `StorageError`. The check: the 50 seeded events are still first in the queue, the stored count is the number of reported successes (plus at most one event whose commit failed after it was written), and `PRAGMA integrity_check` is `ok`. After the filler is deleted, `track()` succeeds and the queue is delivered. The filler is deleted in `finally`, and in the script trap.
3. **A WorkManager failure is real, by a write lock.** `FaultPhases.workmanager_fault` holds the write lock of `androidx.work.workdb` with a second SQLite connection. Every WorkManager enqueue then fails after the busy timeout with `SQLiteDatabaseLockedException`. `SignalDock.initialize()` and `track()` succeed, the events are stored, foreground delivery works, and the SDK logs the WARN "WorkManager request failed". After the lock is released, the next `track()` enqueues the Worker again. A read-only database file was tried first (`chmod 444`): Android restored the file mode and WorkManager worked, so it is not a usable fault. A corrupt file was not tried, because the framework deletes and recreates a corrupt database by default.
4. **Power loss is not tested.** No emulator can cut power in the middle of a write. The semantics are fixed in words instead: **a committed event survives process death (SIGKILL, crash, OOM kill), not power loss.** The queue is a Room database in WAL mode with `synchronous=NORMAL`. In WAL mode, `NORMAL` does not call fsync at commit; the system syncs the WAL file at a checkpoint. A power cut or an OS crash can lose the last commits, and the database stays consistent. `FULL` would close this gap at the cost of one fsync per `track()`. The first release keeps `NORMAL`: it is the Android default for WAL, and the design already accepts the loss of unsent events in other cases (ADR-0001: data clear, reinstall). This is an implementer decision that the user can change. Gap: the cost of `FULL` was not measured.
5. **The setting is pinned by a test.** `PowerLossSemanticsDeviceTest` reads `PRAGMA journal_mode` and `PRAGMA synchronous` from the SDK's own connection and asserts `wal` and `1` (`NORMAL`). It runs in a plain `connectedDebugAndroidTest`. If a change moves the SDK to `FULL`, or a device default changes the value, the test fails and this ADR must be updated. A new plain connection would report its own default, so the test asks the connection that Room opened.
6. **Cases and cleanup.** The script has three new cases: `airplane`, `fulldisk`, `workmanager`. `scripts/device-durability.sh` runs them by default, and its `EXIT` trap restores airplane mode, deletes the filler file and stops the host server. The three phases change global emulator state: the script keeps its rule that only `emulator-*` serials are accepted.

## Limits

- The results are from one emulator image (API 37.2, `google_apis_ps16k`, arm64). A physical device or another OEM image can behave differently, for example a different `synchronous` default (decision 5), a different reserved block size, or a different airplane-mode implementation.
- The full-disk case uses an app-visible filler file. System services also write to `/data`, so the exact point of failure is not fixed. The test does not depend on it.
- The WorkManager fault is a database write lock. It does not prove behavior for a WorkManager that is not initialized (host disabled the initializer): that case stays with `SchedulingTest` and `CrashSafetyTest` on the JVM.
- Power loss is still untested. The semantics are documented and pinned; the behavior is not observed.
- CI does not run these cases (ADR-0011 decision 10).
