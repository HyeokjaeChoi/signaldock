# SDK device measurement harness (issue 24)

Spec section 7 fixes the loads (synthetic events of about 1 KiB; normal 1 event/s for 60 s; offline accumulation of 1,000 events; burst 100 events/s for 10 s), the facts to record, and the rule that a run which misses the target rate is not a success. It leaves open the server, the build mode, and the way to time, count, and compare. This ADR records those choices. They are implementer decisions that the user can change. They add no product behavior and change no product code or default.

## Decisions

1. **Server: the real Ktor + PostgreSQL stack from `docker-compose.yml`, in a separate Compose project.** Duplicate and missing events can only be settled against stored rows, so the in-test `AckServer` of ADR-0011 is not enough here. The stack runs with its own project name (`signaldock-sdkmeasure`), its own ports (server 18090, DB 15440 in the runs), keys and DB password generated for the run in an env file outside the repo, and the Dashboard container left out. The server has the product settings (no benchmark profile, no Docker limits). `scripts/device-measure.sh` does not start or stop it, never runs `docker compose down`, and never deletes a volume.
2. **Path: emulator, `10.0.2.2`, the existing pass-through proxy, server.** The proxy `scripts/e2e/fault-proxy.py` in `pass` mode (ADR-0010) logs every batch the SDK sends, with its event IDs and the server answer. That gives the number of requests, the IDs that were sent more than once, and the ACK statuses (`accepted`, `duplicate`) without any new code. Cost: one local hop of a few milliseconds in each delivery. It does not touch `track()` timing (a Room write on the device) and it adds to drain time. The numbers are for this path.
3. **Build mode: debug, instrumented.** The SDK is a library, so it runs inside the androidTest APK (ADR-0011 item 1): the library's debug variant, `debuggable`, no R8, no minification, the default JIT of the AVD image. A release R8 build exists only in the consumer app (ADR-0010), which has a UI and no hook to run these loads. Release numbers would be faster or equal; a debug build is the conservative side. Every run records `debuggable` and the build text.
3a. **Public path.** The phases call `SignalDock.initialize` with product defaults: real Room, real OkHttp (30/10/10/10 s timeouts), real WorkManager, the foreground trigger (20 events or 10 s), and the retry policy. No seam of `createSdk` is used.
4. **Event.** One event name per run (`m_<runId>`; a run ID is unique, so a server query by name returns exactly the events of the run), properties `seq`, `run`, and a fixed ASCII `pad` text. The text length is tuned so that the SDK's own size of one event as sent (`sizeBytes`, read from the first queued row) is about 1,024 bytes; the runs show 1,024 to 1,026. A run is valid when the size is 900 to 1,150 bytes. The size includes the common fields of the contract.
5. **Injection and timing.** Normal and burst are open loop: call `i` starts at `i / rate` after the start, each on its own coroutine (`Dispatchers.Default`), so slow calls overlap and never slow the schedule. `track()` completion time is `System.nanoTime()` around the suspend call, from before the call to its return, per call, in microseconds. Offline accumulation is back to back (concurrency 1): the spec gives no rate for it, so the actual rate is a result, not a target. Percentiles use nearest rank (same function as `perf/summarize.py`). Maximum calls in flight is counted in the test. Start lateness (actual minus scheduled start) is recorded per call.
6. **Offline.** Two processes, because the SDK configuration is fixed per process (Q113). Process 1 uses an unreachable endpoint (`http://127.0.0.1:9`); the SDK tries and fails and persists a retry time. The script then force-stops the app (as ADR-0011 item 4) and process 2 starts the SDK with the reachable endpoint. The SDK delivers by itself and honors the persisted retry time (ADR-0011 item 6). Drain time of process 2 therefore includes that wait; the summary shows the wait and the drain time after it (the wait is 0 when the persisted time has passed before the restart). Process 1 first waits until diagnostics show a failed attempt and a persisted retry time (limit 60 s), so the restart always has a persisted retry state.
7. **Drain time.** From the end of the last `track()` call (offline: from the SDK start of process 2) until `diagnostics().queuedEvents == 0`, polled every 50 ms, limit 5 minutes (offline 10 minutes). Queue empty means the ACK was applied. Without delivery tuning, normal and burst events leave through the SDK's own triggers.
8. **Files.** Sizes in bytes of every file in the SDK directory (`noBackupFilesDir/signaldock`: `queue.db`, `queue.db-wal`, `queue.db-shm`, `installation-id`), at the end of injection and after drain. The WAL is not checkpointed on purpose; its size is part of what the host sees.
9. **Memory.** In-process `Debug.getMemoryInfo().totalPss` and the Java heap (`Runtime`), in KiB. Reads: before initialization and after initialization (each after `System.gc()` and 300 ms), at the end of injection (no GC, so the drain clock is not delayed), after drain (after GC). The report uses the change after initialization, so Room and WorkManager start-up cost is separate from the cost of the events. Android reports PSS with noise of some MiB; the numbers show size order, not exact cost. `dumpsys meminfo` is not used: it gives the same PSS from outside and adds a process call that can disturb the run.
10. **Reconciliation.** After each run the script reads the event IDs of the run from PostgreSQL (`docker compose exec db psql`). Missing = IDs for which `track()` returned `Success` but that are not stored. Not tracked = stored IDs that no `track()` returned. Duplicate rows = repeated IDs in the stored rows (the primary key makes this 0; it is still checked). From the proxy log: events sent, IDs sent more than once, batches not answered with 200, ACK status counts.
11. **Verdict.** `invalid`: a phase did not finish; fewer calls started than planned; for normal and burst, an actual start rate `(n-1)/(last start - first start)` below 95 % of the target; event size not measured or outside 900 to 1,150 bytes; no calls file, no proxy log, or tracked events that the proxy log never saw (the evidence is incomplete). An `invalid` run is kept with its reason and is never a pass. `fail`: a `track()` result other than `Success`; missing, not tracked, or duplicate rows; a queue that does not drain in the limit. `pass`: none of these. There is no latency threshold: the spec guarantees no ceiling or throughput, and the numbers are measured in this environment, not an SLA. IDs sent more than once are recorded but are not a failure by themselves.
12. **One run per AVD and scenario, run one AVD at a time.** The host also runs other work, so the host model, CPU count, load average before and after, and git revision are stored in `meta.json`. There are no repetitions: one run shows the order of magnitude, not a distribution.
13. **Layout.** Raw and derived files are in `perf/sdk-results/<api>-<scenario>/` (`calls-<phase>.csv` with one row per call, `result-<phase>.json` from the device, `db-ids.txt`, `proxy.jsonl`, `meta.json`, `run.json`, `summary.md`), and the combined table is `perf/sdk-results/summary.md`. It is not under `perf/results/`, because `perf/summarize.py` reads every directory there as a server run. The Python reduction is `perf/sdk_summarize.py` (standard library only). Raw files do not hold keys or passwords. The script collects into a temporary directory and replaces the run directory only after collection, so a failed setup keeps the earlier run; files of a failed phase are pulled too. If the database IDs cannot be read, the run is `invalid` (an empty list would look like missing events).

## Not done

- The `perf/report` page and `perf/summarize.py --index` do not show SDK runs. The page takes server runs with a fixed shape, and adding SDK runs means TypeScript, a build, and a second data shape for one table that Markdown already shows. Add it when the portfolio needs a chart.
- No release (R8) build run, no physical device, no repetitions, no thermal or battery control (emulators on a shared host).

## Limits

- Emulator latency depends on the host. The host was not idle (load average is recorded). Values are not comparable with a phone.
- The proxy is Python on the host. Its cost is part of drain time, not of `track()` time.
- Memory numbers include noise (decision 9).
