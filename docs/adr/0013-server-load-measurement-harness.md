# Server load measurement harness decisions

Issue 23 builds the harness and the pilot for `.scratch/signaldock-portfolio/performance-plan.md`. The plan fixes limits, seeds, load, durations, and acceptance. Spec section 11 and Q124 to Q125 keep benchmark values apart from normal runtime values. These decisions fill the gaps those sources leave. They are implementer decisions that the user can change.

**Layout.** The harness lives in `perf/`. `perf/compose.perf.yml` is an override of `docker-compose.yml`. The scripts always call Compose with `-p signaldock-perf`, so containers, network, and the DB volume (`signaldock-perf_signaldock-db`) are separate from the default stack. The default `docker compose up` does not read `perf/`. The override sets DB 2 CPUs / 2 GiB and Ktor 2 CPUs / 1 GiB with `-Xmx512m`, and the plan's benchmark profile. It does not start the Dashboard. PostgreSQL settings stay at the defaults of the pinned image; each manifest stores the effective settings. Host ports are 15432 (DB) and 18080 (server). Test keys and the DB password are random, live in `perf/work/env` (gitignored, mode 0600), and are never written to a manifest or a result.

**Product code change: env settings with unchanged defaults.** The benchmark needs pool size, `minimumIdle`, concurrency, and wait limits that the server did not expose. `DatabaseLimits` gets `minimumIdle` (default 0, as before). `Application.kt` reads `SIGNALDOCK_DB_POOL_SIZE`, `SIGNALDOCK_DB_POOL_MIN_IDLE`, `SIGNALDOCK_DB_CONCURRENCY`, `SIGNALDOCK_DB_ADMISSION_MS`, `SIGNALDOCK_DB_CONNECTION_MS`, `SIGNALDOCK_DB_LOCK_MS`, and `SIGNALDOCK_DB_STATEMENT_MS`. With none set, the limits equal `DatabaseLimits()`, so ADR-0004 values stay the runtime defaults. `SIGNALDOCK_POOL_STATS_MS` (default off) logs `active/idle/pending/total` of the pool. This adds no contract change and no normal runtime value.

**Benchmark profile.** The plan names admission 1 s, connection 1 s, statement 2 s, client timeout 5 s, concurrency 8. The plan gives no lock limit; Q125 and `architecture.md` require `lock_timeout < statement_timeout`, so the harness uses 500 ms. The server request budget stays at its 5 s default, equal to the client timeout. The server applies statement and lock limits with `SET LOCAL` on the connection of each query. That is narrower than the role or session scope in the plan and cannot reach Flyway or jOOQ generation, so no `ALTER ROLE` is used.

**Seeds.** `perf/seed.py` generates rows with a fixed seed: exactly 70/20/10 types, installation IDs round-robin over 100 values, events of 1,024 bytes as event JSON, `received_at` in [T-30d, T) sorted into physical insert order. Time and type are drawn independently. `uniform` and `recent70` (70 % in the last 24 hours) are the two distributions. T is Asia/Seoul midnight of the build day and is stored with the seed. A template database `base_schema` is migrated by the real server, so the schema and Flyway history are the product's own. `seed_<size>_<dist>` is created from it, loaded with `COPY`, and `VACUUM (ANALYZE)`d. Every run restores `bench` with `CREATE DATABASE ... TEMPLATE`, then runs `ANALYZE` and `CHECKPOINT`. Because live rows get `receivedAt` at or after T, queries over [T-N, T) never see rows written by the run; the aggregate expectation is constant and checked in every response.

**Load.** `perf/load.js` runs one k6 process: the collection scenario (constant-arrival-rate, 5 requests/s of 20 events, 30/30 VUs, 5 s timeout, no retry) and one `constant-vus` scenario per Dashboard endpoint (list with `limit=50`, by-name, by-time with the default bucket), one VU per client and endpoint. A tick that finds its previous request still running is skipped and counted. Event IDs follow `<8-hex run salt>-0000-4000-8000-<12-hex event number>`, so the runner can match stored rows to requests. Request bodies are generated before the run from one fixed seed. k6 starts one extra iteration at the end of the duration; it is tagged `tail`, kept in reconciliation, and not counted as a measurement iteration.

**Run result.** `perf/run_one.py` restarts the server for every run, so each run has a fresh JVM and pool. A run is `invalid` when the load did not match the plan (dropped iterations, fewer than 1,500 measurement iterations started, pool not ready, DB work after a 30 s drain), `fail` when a criterion is missed, and `pass` otherwise. A pilot is recorded with `counts_as_measured_run: false`. `perf/matrix.py` lists and resumes the 216 runs. `perf/summarize.py` writes Markdown, a per-minute trend table, and figures. Python here has no matplotlib, so it writes CSV for later plotting when matplotlib is missing.

**Not collected.** There is no `pg_stat_statements`, so DB query time per statement is not measured. Hikari acquire time is the server's `connection_wait` stage. Physical disk I/O is not measured.
