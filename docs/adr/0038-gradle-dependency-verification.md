# Gradle dependency verification (issue 68, spec Q166)

The user approved this item on 2026-10-17 UTC. This ADR records the implementer decisions. The user can change them.

## Context

- Gradle downloads every dependency and plugin from Maven Central, Google Maven, and the Gradle Plugin Portal. Before this change, nothing checked that a downloaded file is the file that we used before. A changed file on a registry, or a changed file in transit, would enter the SDK, the server, and the CI runners without a signal.
- Gradle can check each file against a list in `gradle/verification-metadata.xml`. When a file is not in the list, or its checksum differs, the build fails ([Gradle docs, "Verifying dependencies"](https://docs.gradle.org/current/userguide/dependency_verification.html)).
- This repo has four independent Gradle builds with their own wrappers: `sdk/`, `server/`, `contract-check/`, and `compatibility/consumer-android/` (Q89). Gradle reads only the file in the root project of the build, so there are four files. The version catalog is shared; the metadata is not.
- Renovate opens weekly dependency PRs (ADR-0031). The first runs start on Monday 2026-10-19 UTC. A new version has new files, so each such PR changes what the metadata must list.

## Decisions

1. **SHA-256 checksums only. No PGP signatures.** `<verify-metadata>true</verify-metadata>` and `<verify-signatures>false</verify-signatures>`.
   - What public projects do: AndroidX uses checksums and signatures, with `key-servers` off and about 300 `trust` entries, among them Google's own R8, aapt2, and bundletool, so even Google cannot sign everything ([androidx `gradle/verification-metadata.xml`](https://raw.githubusercontent.com/androidx/androidx/master/gradle/verification-metadata.xml)). Signal-Android uses checksums only and its own regeneration task ([Signal-Android `gradle/verification-metadata.xml`](https://raw.githubusercontent.com/signalapp/Signal-Android/main/gradle/verification-metadata.xml)). Checked on 2026-10-17 UTC: sentry-java, okhttp, dd-sdk-android, posthog-android, retrofit, mixpanel-android, purchases-android, and firebase-android-sdk have no `gradle/verification-metadata.xml` on their default branch. So this is not a common practice among SDK repos, and the choice here is a supply-chain hardening beyond what they do.
   - Why not signatures: Gradle supports only ASCII-armored `.asc` files, not every artifact has one, and a valid signature proves only that some key signed the file, so each new publisher key needs a trust decision ([Gradle docs](https://docs.gradle.org/current/userguide/dependency_verification.html)). That is a decision in every Renovate PR for a one-maintainer project. Checksums need no decision: the diff shows which files are new.
   - Limit (accepted): a checksum is trust on first use. The file records what Gradle downloaded when the metadata was written. It catches a later change of a file. It does not catch a file that was already bad at that time. Signatures are the later path, and the current file works with them (`--write-verification-metadata sha256,pgp`).
2. **One file for each build,** at `<build>/gradle/verification-metadata.xml`: 4 files, 690 (`sdk`), 212 (`server`), 64 (`contract-check`), and 366 (`consumer-android`) components.
3. **Coverage is what CI runs.** `scripts/update-gradle-verification.sh` runs `--write-verification-metadata sha256` over the tasks of the CI jobs: `build` (compile, unit tests, lint, R8 `assembleRelease`), `assembleDebugAndroidTest`, `apiCheck`, `dependencyGuard`, the Maven ZIP, the CodeQL manual build tasks, `verifyJooq`, and the consumer R8 builds with and without the SDK. A configuration that no task resolves is not covered. The script gives each Gradle run an empty Gradle home (`GRADLE_USER_HOME`). With a warm cache, Gradle does not record files that it cached earlier, such as BOMs and parent POMs. The first CI run (cold cache) of this change failed on them, first for a warm home, then for one home that the four builds shared. Do not run `--write-verification-metadata` by hand with your normal Gradle home.
4. **`local.signaldock` is trusted in `consumer-android`** (`<trust group="local.signaldock"/>`). The consumer reads the SDK from a folder that the script builds, and the checksum of that AAR changes at each build. This is the only `trusted-artifacts` entry.
5. **The aapt2 jar of both OS is listed.** Gradle writes only the file for the OS that runs it: `aapt2-<version>-osx.jar` on a Mac, `-linux.jar` on the CI runner. The script adds the other one. It downloads it from Google Maven over HTTPS and computes the checksum. For the macOS file, this checksum is equal to the one that Gradle wrote, so the method matches Gradle's. Other OS-specific files (the Netty native jars) are listed for all OS by Gradle through the module metadata.
6. **Renovate does not update these files for this repo. The author does it.** Finding, with sources:
   - Renovate has the feature: if `gradle/verification-metadata.xml` has `<verify-metadata>true</verify-metadata>` or `<verify-signatures>true</verify-signatures>`, it runs `./gradlew --write-verification-metadata <hash types> dependencies` ([Renovate docs, Gradle manager, "Dependency verification"](https://docs.renovatebot.com/modules/manager/gradle/)). It needs the self-hosted administrator to allow `gradleWrapper` in `allowedUnsafeExecutions`, and Renovate "does not support Android projects that require extra configuration to run (e.g. setting the Android SDK)" ([Renovate docs, Java](https://docs.renovatebot.com/java/)). Gap: the Mend-hosted docs do not say whether the Community app allows `gradleWrapper`; the allowed `postUpgradeTasks` commands are "not documented" ([Mend hosted apps config](https://docs.renovatebot.com/mend-hosted/hosted-apps-config)). We could not confirm it, and we do not rely on it.
   - Even when it is allowed, the code in `lib/modules/manager/gradle/artifacts.ts` ([Renovate source](https://github.com/renovatebot/renovate/blob/main/lib/modules/manager/gradle/artifacts.ts)) does not fit this repo: (a) it looks for `gradlew` upward from the changed file. The shared catalog `gradle/libs.versions.toml` is in the repo root, and no `gradlew` is above it, so Renovate stops (the debug log says "no gradlew - aborting update") for every catalog update; (b) it uses the first `gradle/verification-metadata.xml` in the file list, and there are four; (c) it runs only `dependencies`, which resolves the root project, not the test, lint, R8, and subproject configurations that CI uses, so a file that Renovate writes would still miss entries.
   - Result: every Renovate Gradle PR will fail the Gradle CI jobs until the author runs `scripts/update-gradle-verification.sh` on the PR branch and pushes the four files. This is the lowest-friction path that stays safe: the author sees a normal failing build, the fix is one command, and the diff of the metadata shows exactly which new files came in. ADR-0033 already needs a manual step on some Renovate PRs (`dependencyGuardBaseline`), so the weekly routine has one more step of the same kind.
   - Cost: some minutes of build time and a push for each Renovate PR (up to 4 open at once, ADR-0031). Renovate stops rebasing a branch that a person edited, so push once, after the last update of that PR. Group PRs (ADR-0031 item 4) keep the count low.
   - Rejected: (i) a workflow that commits the metadata to Renovate PRs. It needs a write token on a workflow that runs the code of a PR, and a push with `GITHUB_TOKEN` does not start CI. That is a new supply-chain risk for a small gain. (ii) `postUpgradeTasks` in the hosted app: not documented, no Android SDK on the Renovate runner. (iii) Turn verification off for Renovate PRs: it would let the files that matter most go unchecked. (iv) Wait for Renovate to support it: not needed, the manual step is short.
7. **No new CI step.** The Gradle jobs already fail on an unknown or changed file, with Gradle's own message. `CONTRIBUTING.md` and `docs/releases/README.md` give the command. Gap: the Gradle message does not name the script. If this costs time, add an `if: failure()` hint step to the Gradle jobs of `.github/workflows/repo-rules.yml`.

## Gaps

- Checked in CI (PR #181, Linux, cold cache): every Gradle job passes, among them `device-test` with `connectedDebugAndroidTest`, so the aapt2 handling of item 5 and the cold-cache rule of item 3 work. Another OS-specific file would fail a job with a clear message.
- Gap: Robolectric downloads its `android-all` jars at test run time by itself, not through Gradle, so they are not verified here. The Gradle wrapper distribution is guarded by `distributionSha256Sum` and the `gradle-wrapper` job. The JDK, `oasdiff`, and the OpenAPI generator are guarded by `scripts/setup-toolchain.sh`, npm by `package-lock.json`, and images by digests.
- Gap: Gradle only adds entries. A removed dependency leaves a stale entry. This is harmless. To prune, delete the `<components>` block of one file and run the script again (the `trusted-artifacts` block stays).
- Gap: the unit test of `:demo:core:data` fails on `main` (an `http` endpoint without `allowInsecureEndpoint`, ADR-0035). CI does not run it. The script excludes that one test task and compiles its tests, so the metadata may lack a file that only that test run resolves. Remove the exclusion when the test is fixed.
