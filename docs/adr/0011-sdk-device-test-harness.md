# SDK device test harness and process-boundary simulation (issue 20)

The design sources leave the test harness open (spec section 7 "Offline recovery", "Concurrency", "Collection cancellation", "Capacity boundaries", "Installation lifetime"; section 9 item 5). This ADR records the choices made in issue 20. It adds no product behavior and changes no product code. ADR-0003 decision 8 and ADR-0006 "Not verified here" named the gaps that these tests close.

## Decisions

1. **Instrumented tests live in `sdk/sdk-android/src/androidTest`, not in a new module.** They call `createSdk` (the composition point with its test seams), the DAO and `InitCoordinator.default`, which are `internal`. Kotlin `internal` is per module (ADR-0005), so only the SDK module's own test sources can use them. A separate `sdk-test` module would have forced public test hooks. The library's test APK is the app under test: package `local.signaldock.test`, with the SDK in its own process, its real `noBackupFilesDir`, real WorkManager, real Room and real OkHttp. `INTERNET` and cleartext HTTP to localhost come from `src/androidTest/AndroidManifest.xml`, because the SDK library declares no permissions (README: the host declares `INTERNET`).
2. **The server is a MockWebServer on the device, not the Compose stack.** `AckServer` (`mockwebserver3` 5.4.0, the OkHttp version of ADR-0006) answers like the ingestion server for ACK purposes: first sight of an `eventId` is `accepted`, later `duplicate`. It can delay, return 503, or commit and then close the socket (lost ACK). The Compose server has its own tests (server issues); here it would only add a dependency on Docker and on `10.0.2.2`.
3. **Per-test isolation.** `Rig` gives each test its own `noBackupFilesDir` (`IsolatedContext`), its own coroutine scope, and a fresh `InitCoordinator.default` (a `var` for tests, ADR-0006) so the real `DeliveryWorker` finds that test's SDK. It cancels all WorkManager work afterwards. Tests that must not send use `NoopScheduler`; the contention test uses the real `WorkManagerScheduler`.
4. **A process restart is a new instrumentation run after `am force-stop`.** `DurabilityPhases` holds one JUnit method per phase. A phase runs only with `-e phase <name>`, so a plain `connectedDebugAndroidTest` skips them. `scripts/device-durability.sh` runs `am instrument` for a phase, then `adb shell am force-stop local.signaldock.test` (SIGKILL), then the next phase in a new process. Each phase reports its process ID; the script fails if two phases share one. The kill-during-collection case force-stops the app while a loop calls `track()`, and writes each reported success to an fsynced log; the next phase checks that every logged ID is in the queue, that at most one unlogged in-flight event is stored, and that `PRAGMA integrity_check` says `ok`. Before the SDK starts again, the queue file is read with plain `SQLiteDatabase`, without the SDK, and compared with a snapshot (event ID and SHA-256 of `payloadJson`).
5. **Installation transitions.** Update is `adb install -r -t` of the same APK over the installed package. Clear is `pm clear`. Reinstall is `adb uninstall` then `adb install`. Restore is Auto Backup on a local transport: `bmgr enable true`, select the `LocalTransport`, `bmgr backupnow`, uninstall, install, `bmgr restore <token> <package>`. A host marker file in `filesDir` is the control: the restore case passes only if the marker came back (so a restore really ran) while the SDK directory in `noBackupFilesDir` did not. Backup Manager is switched off at script start and end, because with auto-restore on, a plain reinstall brings back host data of an earlier backup. The seed phase reports the installation ID and event IDs; the script passes them to the check phase as instrumentation arguments, because the app's own data does not survive the transitions.
6. **Delivery timing in the restart case is not forced.** The recovery phase starts the SDK through the public `SignalDock.initialize` and waits for the real Worker (scheduled at initialization because the queue is not empty) to deliver, honoring the retry time that the offline phase persisted. No test calls the sender directly there. The wait limit is 5 minutes.
7. **Logcat checks.** Tests read the SDK's own lines with `logcat -d -s SignalDock:V` and compare with a snapshot taken before the action, because the buffer keeps earlier tests' lines. logd merges identical consecutive lines, so counts of repeated WARNs use a recording `Logger` next to the real `AndroidLogger`.
8. **Instrumentation output.** Phases print status with `Instrumentation.sendStatus` (`INSTRUMENTATION_STATUS: key=value`); `addResults` needs API 26.
9. **Pins.** `androidx.test:runner` 1.7.0 and `androidx.test.ext:junit` 1.3.0 (latest stable on Google Maven, 2026-10-12), next to `androidx.test:core` 1.7.0. Test method names use underscores, because backtick names are not valid in DEX before API 30.
10. **CI compiles the instrumented tests.** The `sdk-test` job adds `:sdk-android:assembleDebugAndroidTest`. Since issue 40 the `device-test` job also runs them on an emulator (ADR-0023); the process-boundary script `scripts/device-durability.sh` stays local.

## Limits

- The update case installs the same build over itself. It shows that data survives a package replace, but not an update that changes the SDK version or the Room schema (no schema migration exists yet, ADR-0003 decision 7).
- The `offline` case uses a refused connection to `127.0.0.1:9`, not an airplane-mode switch. The SDK sees `NETWORK` failures either way (ADR-0006 decision 5). ADR-0029 adds a real airplane-mode case.
- Auto Backup was exercised through the local transport, not the Google transport, device-to-device transfer or manufacturer tools (ADR-0001: not guaranteed).
- `SIGKILL` through `am force-stop` does not test power loss. SQLite in WAL mode with the default `synchronous=NORMAL` is durable against process death but not against power loss. ADR-0029 documents this and pins the setting with a test.
- The suites ran on two emulator images (API 24 `google_apis` arm64 and API 37.2), not on a physical device.
