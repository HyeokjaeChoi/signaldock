# Optional tracking plan and code generation (issue 37, spec Q152 to Q154)

The user chose (Q152 to Q154) to build a tracking plan with code generation. It shows one event taxonomy for web and app. The plan is optional, the SDK does not change, and the server does not check the plan. This ADR records the implementer decisions. The user can change them.

## Decisions

1. **The plan is `tracking-plan/plan.json`.** JSON needs no parser dependency in Node, and the repo has no YAML parser. Fields: `version` (1), `kotlinPackage`, and `events`. Each event has `name`, `description`, and `properties`. Each property has `key`, `type` (`string`, `integer`, `number`, `boolean`), `required`, and `description`. These types are the contract value types: a string, a number, or a boolean. `integer` and `number` both go on the wire as a JSON number. `integer` is `Long` in Kotlin because the contract allows plus or minus (2^53 - 1); `number` is `Double`. No null, no nesting, no arrays (spec 3).
2. **Naming convention: lowercase snake_case, an event name has at least two words, at most 64 characters.** The pattern is `^[a-z][a-z0-9]*(_[a-z0-9]+)*$` for event names and property keys. `object_action` is the intent (`product_viewed`), not a check on the words. Why two words: a one-word name (`viewed`, `purchase`) does not say which object, so web and app teams pick different names for one action; two words is the part of `object_action` a pattern can check. Why 64 characters: the contract sets no length limit, so the plan sets one to keep names readable in Dashboard tables and generated identifiers short. It is a plan rule only; the SDK and the server do not change. This is stricter than Q64, which only rejects empty names and names with leading or trailing whitespace, so every valid plan name is also valid for the SDK and the server. The SDK still does not trim or change names (Q64, Q84). A property key that is a Kotlin keyword is rejected. A description is one trimmed line and has no `*/` and no `/*` (Kotlin block comments nest), so it is safe in a comment. Duplicate event names and duplicate keys in one event are rejected, also when two different snake_case names give the same camelCase identifier (`item_1` and `item1`). An event whose function name would be `eventNames` (the generated TypeScript constant) is rejected. A Kotlin keyword in `kotlinPackage` is rejected. The generator exits with code 1 and lists every problem in the plan.
3. **The existing demo events keep their names and keys.** `product_viewed`, `add_to_cart`, `checkout_started`, and `purchase_completed` (with `is_simulated`) already follow the convention. The deliberate change: `price_minor` of `product_viewed` is optional in the plan, so the plan shows an optional property. The demo always sends it, so the wire output is the same.
4. **One generator: `tracking-plan/generate.mjs`, plain Node with no dependency.** Node is already required by the Dashboard build and by `scripts/verify-contract.sh` (step 4), so this adds no tool. The repo has no other scripting stack that fits (the Gradle builds are Android and server builds; `scripts/` holds shell and Python for checks). `generate.mjs` exports `validatePlan` and `generate` for the test. It writes `tracking-plan/generated/`: `kotlin/TrackingPlan.kt`, `typescript/events.ts`, and `manifest.json`. All three come from one in-memory plan, so they cannot disagree because of two templates reading the plan in two ways. Reviewers read `plan.json` and `generate.mjs`, not the generated files (the ADR-0002 amendment rule).
5. **Generated Kotlin: `internal suspend fun SignalDock.productViewed(productId: String, priceMinor: Long? = null): TrackResult`.** It calls `track("product_viewed") { property(...) }`. A required property is a non-null parameter. An optional property is a nullable parameter with default `null`, and it is left out when null (spec 3: no explicit null). Required parameters come first. The file also has `internal object EventNames` with one constant for each event, so `DemoEvent.name` has no second copy of the string. The functions are `internal` to the demo module. The package is `local.signaldock.demo.core.data.tracking`.
6. **Generated TypeScript: types and builders, no web SDK.** `EventInput { name; properties }` is the part of the contract `EventIngest` that the app chooses. Each event has a `...Props` interface (camelCase fields; an optional field has type `T | null` and `?`) and a builder that returns `{ name, properties }`. A property that is `undefined` or `null` is left out. The builders do not validate values: there is no server-side or client-side check of the plan now (Q152). `dashboard/src/contract-check.ts` passes a builder result through the generated `EventIngestFromJSON` and `EventIngestToJSON`, so the shape is checked against the contract models. `dashboard/tsconfig.json` type-checks `events.ts` with the Dashboard code.
7. **The outputs are committed, and a drift check runs in CI.** The pattern is the one of ADR-0002 and ADR-0012: `scripts/verify-contract.sh` step 7 generates into a temporary directory and runs `diff -rq` against `tracking-plan/generated/`. It does not rewrite the checkout (the same as step 1). A `git diff --exit-code` after a regeneration would change the working tree and fail on unrelated local edits. The step needs only Node, so it needs no Android SDK. It then runs `node --test tracking-plan/generate.test.mjs`. Step 7 comes after step 6, so a machine without the Android SDK stops at step 6 first; run the Node commands directly there.
8. **The demo app uses the generated functions; the consumer app and the SDK do not change.** `sdk/demo/core/data` adds `tracking-plan/generated/kotlin` as a source directory (the way `sdk-android` adds `generated/kotlin`). `SdkSignalDockClient` maps each `DemoEvent` to a generated function. `DemoEvent` keeps its data classes for the ViewModels and drops the hand-written property map and `PropertyValue`; `ShopViewModelTest` now compares the event objects. `compatibility/consumer-android` stays on plain `track()`, which shows that the plan is optional. `sdk/sdk-android` has no change, and `:sdk-android:apiCheck` passes with the unchanged dump.

## Test mechanism

`tracking-plan/generate.test.mjs` (Node's built-in test runner, no dependency) has three parts, and one demo test runs the generated Kotlin.

- **Plan validation:** a table of invalid plans (bad names, bad keys, unknown type, duplicates, and so on); each must be rejected with a clear message. Validation checks `typeof` before a value check, so a wrong JSON type (for example an array for `kotlinPackage` or `type`) is a plan error, not a string conversion or an exception. It also checks that the committed outputs equal a fresh generation.
- **TypeScript is run.** The test imports the generated `events.ts` (Node strips the types) and calls each builder with sample values for all properties, then with the required properties only, and with `null` for each optional property. It checks the event name, the property keys, and `typeof` of each value against the manifest.
- **Kotlin is read as text.** For each event, the test parses the generated function: its parameters (name, Kotlin type, nullable), the `track("name")` literal, and the `property("key", param)` calls. It checks the same name, the same keys in the same order, each argument is the parameter of the right plan type, the nullable parameters are exactly the optional properties, and each Kotlin type maps to the same wire type (`String` to string, `Long` and `Double` to number, `Boolean` to boolean) that the TypeScript builder produced.

Why text for Kotlin in the Node test: a real call needs a `SignalDock` instance, and the SDK does not change, so there is no public test seam. The generated file has a fixed shape that the generator controls, so a parse of it is reliable, and the demo build compiles the same file (`:demo:app:assembleDebug`). The Node test does not execute the Kotlin.

The Kotlin is executed in `sdk/demo/core/data` (`SdkSignalDockClientTest`, Robolectric, run by `sdk/gradlew test`). It calls the real `SdkSignalDockClient` for all four `DemoEvent`s on a real SDK instance (`SignalDock.initialize`, real Room, an endpoint where nothing listens, so events stay queued). It reads the stored events from the SDK queue database and checks the event name and every property key and value, including `is_simulated = true` on `purchase_completed`. A wrong mapping in the adapter or a change in a generated wrapper fails this test. It drives the SDK only through its public API, but it reads the SDK's internal queue database (`signaldock/queue.db`, table `events`, column `payloadJson`) to see what was stored, so a change of that schema needs this test updated. It adds only test-only dependencies to the demo module.

## Not done

- No server-side check of events against the plan (Q152). It is possible later as a separate decision.
- No `number` or `integer` range check in the builders (the SDK checks ranges and reports `TrackResult.Invalid`).
- No web SDK, no WebView bridge (Q150), and no plan use in the consumer app.

## Amendment (2026-10-15)

Spec Q155 adds a server-side check after all: the server marks stored events with a plan status and never rejects one. The first "Not done" item above is now done in [ADR-0022](0022-server-tracking-plan-status.md). Everything else in this ADR stands; the SDK and the generated code are unchanged.
